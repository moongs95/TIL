# 데이터 전처리 및 원천 데이터 구축

## 1. 데이터 전처리 개요

### 원천 데이터 구축 시 품질 기준

다양한 방법으로 수집된 원시 데이터가 양질의 원천 데이터가 되기 위한 고려사항:

#### 기준 적합성
- **다양성**: 데이터가 충분히 다양한 케이스를 포함하는가
- **신뢰성**: 데이터 출처와 수집 방법이 신뢰할 수 있는가
- **충분성**: 학습/분석에 필요한 충분한 양의 데이터가 있는가
- **균일성**: 카테고리별로 데이터 샘플 수량이 균형있게 분포하는가
- **사실성**: 데이터가 실제 현상을 정확히 반영하는가
- **공평성**: 특정 집단에 편향되지 않았는가

> 예시: 분류/탐지/예측 등의 카테고리별로 데이터 샘플의 수량이 불균일하게 수집되진 않았는가?

#### 기술 적합성
- 파일 포맷
- 해상도
- 컬러 심도
- 어절 수

#### 통계적 다양성
- 클래스 분포
- 샘플 분포
- 문장 길이
- 어휘 개수

### 데이터 전처리(Data Preprocessing) 정의

데이터에 원하는 처리(processing)를 가하기 이전(pre-)에 데이터를 가공 및 정제하는 모든 과정

#### 관점별 정의

**모델 학습 관점**
- 모델을 학습하기 전, 모델 학습이 용이하도록 데이터를 가공하는 단계

**데이터 구축 관점**
- 데이터에 라벨을 부여하기 전, 원본이 일정 수준 이상의 양과 질을 만족하도록 하는 단계
- 즉, 원시 데이터를 원천 데이터로 만들기 위해 가공 및 정제하는 단계

#### 전처리 vs 클렌징

일반적으로 데이터 클렌징이 데이터 전처리의 하위 개념으로 여겨지지만, 데이터 구축 단계에서는:
- **데이터 전처리**: 라벨링 이전의 정제 과정
- **데이터 클렌징**: 라벨링 이후의 정제 과정

(라벨링이 가장 중요한 '처리' 단계이기 때문)

## 2. 일반적인 전처리

### 도메인 무관 전처리 방법

통상 정형 데이터에 사용되는 도메인 무관 전처리:
- 중복 데이터 처리
- 이상 데이터 처리
- 결측 데이터 처리
- 개인정보 비식별화
- 노이즈 필터링

> ⚠️ 각 전처리 과정이 정말로 필요한지 검토 필요
> - 데이터 활용자 입장에서 전처리를 해서 제공하는 것이 좋을지 판단

### 중복 데이터 처리 (Duplicate Data Handling)

데이터 내에서 동일한 정보나 레코드가 중복되어 나타나는 경우

**처리 방법**
1. **제거(Removal)**: 중복 데이터를 제거하여 정확성 및 균일성 유지
2. **표시(Flagging)**: 중복 데이터를 표시하여 유용한 정보를 유지, 향후 사용자가 분석할 수 있도록 함

> 💡 Best Practice: 중복 데이터가 되지 않도록 추가적인 특성(attribute)을 수집하는 것이 가장 나은 방법

### 결측 데이터 처리 (Missing Data Handling)

수집한 데이터의 일부분에 값이 존재하지 않는 경우

#### Case 1: 수집한 데이터의 소스 내에 결측치가 존재하는 경우
예: 오픈 소스 데이터 내에 이미 결측치가 존재

**처리 방법**
1. **대체(Imputation)**: 결측치를 다른 데이터의 값을 참고하여 대체
   - 평균, 중앙값, 최빈값 등을 사용
   - 예측 모델을 사용하여 해당 값을 대체
2. **제거(Removal, Drop)**: 결측치를 포함한 행 또는 열을 제거

#### Case 2: 수집하는 방식에 허점이 있는 경우
예: 크롤링 시 예외처리가 되지 않은 부분에 의한 오류

**처리 방법**
- 수집 방법을 검토 및 수정
- 또는 Case 1의 방법들 적용

### 이상 데이터 처리 (Outlier Handling)

#### 이상치(Outlier, Anomaly)의 정의
나머지 데이터들로부터 극단적으로 멀리 떨어진 관측치

- '멀리 떨어진'이라는 것은 주관적인 의미를 내포
- 전처리해야 하는 값인지 정상적인 값인지 판단하려면 **도메인 지식**이 필요

**처리 방법**
1. **제거(Removal)**: 가장 간단한 방법이나, 정보 손실 발생 가능
2. **대체(Imputation)**: 이상치를 통상적인 다른 값으로 대체
3. **표시(Flagging)**: 이상치인지 여부를 표시하는 라벨 생성

## 3. 도메인 관련 전처리

데이터의 도메인에 따라 그에 상응하는 품질 기준 및 전처리 방법이 존재

### 도메인별 대표 파일 포맷

| 데이터 유형 | 파일 포맷 | 비고 |
|------------|----------|------|
| 이미지 | JPG, PNG, TIFF | 의료 등 전문 분야의 경우 해당분야 표준 준수 |
| 비디오 | MP4, AVI | 무압축 방식으로 프레임 이미지 시퀀스의 묶음 형태 |
| 오디오 | WAV, PCM | - |
| 텍스트 | - | UTF-8 인코딩 준수 |
| 정량 수치 | CSV | 산업용 센서의 경우 해당분야 표준 준수 |
| 로그 | JSON | 웹표준 준수 |

### 이미지 데이터 전처리 예시

#### 규격 미달 이미지 제거
- 가로 또는 세로의 픽셀이 720px 이하인 경우 → **자동화 코드**
- 24비트(RGB) 컬러 이미지가 아닌 경우 → **자동화 코드**
- GIF처럼 움직이는 이미지인 경우 → **자동화 코드**
- 이미지가 흔들리거나 아웃포커싱된 경우 → **사람 검수**

#### 기타 처리
- 수집 목적과 관계 없는 이미지 제거
- 모든 이미지의 포맷을 JPG로 변환

### 텍스트 데이터 전처리 예시

> 개인정보 비식별화, 노이즈 필터링 등의 전처리 외 추가 사항

#### 어휘 기준 미달 텍스트 제거
- 이모티콘으로만 구성되었거나 ㅋㅋㅋ, ㅎㅎㅎ처럼 초성으로만 구성된 경우
- 한 문장에 포함된 단어의 수가 지나치게 적을 경우
  - 문어체: 평균 15어절 기준
  - 구어체(대화): 평균 5어절 기준
  - → Rule-based로 제어하여 자동화, 반복도 detection 가능
- 대화방 출입, 이미지/파일 등의 공유로 인해 생성된 메시지인 경우

#### 텍스트 정규화
- 이모티콘 및 특수문자는 일부분 또는 전부를 공백으로 변환
- 모든 텍스트의 포맷을 UTF-8 인코딩을 사용하는 txt 파일로 변환

## 4. 원천 데이터 만들기

### 데이터 스키마 설계 (Design Data Schema)

데이터를 데이터베이스에 어떻게 저장할 것인지의 구조(schema)를 설계하는 과정

#### 데이터 구축 관점에서의 스키마 설계
- 어떻게 데이터 라벨링을 진행할지 기획
- 데이터셋이 필요로 하는 정보를 모두 담을 수 있도록 주석(annotation) 작업 설계

#### 스키마 설계 예시

**의미 분할 (Semantic Segmentation)**
- 어느 정도 수준으로 분할할 것인지

**문서 요약 (Document Summarization)**
- 어느 정도 양으로 정보를 압축할 것인지
- 추출 요약 vs. 추상 요약

**감성 분석 (Sentiment Analysis)**
- 전체 텍스트에 대한 한 개의 라벨링
- vs. 텍스트에서 언급하는 요소별로 라벨링

### 데이터 저장 및 관리

#### 디렉토리 구조 설계 원칙

실제 원천 데이터 및 라벨링 데이터는 **파일 디렉토리 형태**로 구성되어 배포됨 (DB가 아님)

**설계 조건**

1. **디렉토리 레벨**: 2~3 수준을 넘지 않도록 구성
   - 하나의 데이터 샘플에 관한 정보는 딕셔너리 형태(JSON)로 저장하는 것이 용이

2. **네이밍 규칙**: 리눅스 환경을 고려하여 영문으로 작성
   - ❌ 한글, 특수문자(괄호, 언더바 외) 사용 불가
   - ✅ 사용자가 이해하기 쉬운 형식 및 용어 사용

3. **경로 표기**: 상대 경로 사용
   - 절대 경로는 사용자마다 다르기 때문에 상대 경로로 표시
   - ❌ `C:\data\raw\raw_0001.jpg`
   - ✅ `..\raw\raw_0001.jpg`

## 핵심 요약

### 데이터 전처리 프로세스
```
원시 데이터
    ↓
[데이터 전처리]
- 중복/결측/이상치 처리
- 도메인별 전처리
- 품질 기준 검증
    ↓
원천 데이터
    ↓
[라벨링]
    ↓
[데이터 클렌징]
    ↓
학습용 데이터셋
```

### 체크리스트
- [ ] 품질 기준 만족 여부 (기준/기술/통계적 적합성)
- [ ] 중복/결측/이상치 처리 방법 결정
- [ ] 도메인별 전처리 방법 적용
- [ ] 데이터 스키마 설계 완료
- [ ] 디렉토리 구조 설계 (2~3 레벨, 영문, 상대경로)
- [ ] 파일 포맷 및 인코딩 통일
