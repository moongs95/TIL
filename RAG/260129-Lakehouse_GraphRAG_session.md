### 세션 1: 데이터 인프라 아키텍처의 이해

### 데이터 레이크하우스의 필요성

- AI 시대에는 이미지, 텍스트, 로그 등 비정형 데이터가 80% 이상을 차지하며, 전통적인 데이터 웨어하우스로는 AI 수요를 감당하기 어려움
- 데이터 레이크하우스는 데이터 웨어하우스의 성능과 데이터 레이크의 유연성을 결합한 저장소 개념
- 비정형 데이터를 효율적으로 다루고 비용 절감과 성능 개선을 동시에 달성

### Parquet 파일 포맷의 효율성

- 레이크하우스의 핵심 기술은 Parquet 파일 포맷
- 열 기반 구조로 필요한 컬럼만 선택적으로 읽을 수 있어 압축률이 높고 읽기 속도가 빠름
- CSV나 JSON 같은 행 기반 포맷은 불필요한 데이터까지 읽어야 하지만, Parquet은 필요한 컬럼만 추출 가능

### 실시간 스트리밍의 중요성

- 배치 처리(일/시간 단위)로는 데이터의 최신성을 보장하기 어려움
- 실시간 스트리밍(Kafka 등)을 통해 데이터 발생 즉시 분석 및 서빙이 가능
- AI 모델이 실시간으로 데이터를 공급받아 재학습 및 추론을 수행하는 파이프라인 필요

### 데이터 품질과 드리프트

- Garbage in, garbage out - 고품질의 정제된 데이터가 필수적
- 데이터 드리프트(분포 변화) 감지 및 자동 재학습 시스템 구축 필요

### 세션 2: AI 모델링과 에이전트 설계

### 하이브리드 서치

- 단순 벡터 검색은 의미적 유사성은 잘 찾지만, 제품 모델명 같은 정확한 키워드 매칭에는 약함
- 키워드 검색과 벡터 검색을 결합하고 리랭킹(RRF 등) 알고리즘을 적용해야 실용적인 솔루션 완성
- 가중치 조정, RRF, 리랭킹 등 다양한 방법론을 데이터 도메인과 상황에 맞게 적용

### 그래프 RAG

- 기존 RAG는 문서에서 유사한 내용을 검색하는 방식
- 그래프 RAG는 문장 간 관계성까지 포착하여 환각 현상을 획기적으로 감소
- 사람의 뇌처럼 개념 간 연결고리를 통해 기억하고 검색하는 방식 (예: 스티브 잡스 → 애플 → iOS)

### 멀티 에이전트 시스템

- 단일 에이전트에 모든 작업을 맡기면 모델이 커질수록 성능이 저하될 수 있음
- 기능별로 분업화된 여러 에이전트를 만들고, 상위 슈퍼바이저가 관리하는 구조
- 예시: 검색 에이전트, 글쓰기 에이전트, 검수 에이전트를 분리하여 각자의 역할 수행
- LangGraph 같은 도구로 에이전트 간 상태 관리 및 워크플로우 제어

### 세션 3: 데이터 엔지니어의 넥스트 커리어

### 모든 역량이 필요한 시대

- 생성형 AI의 발전으로 지식 습득 속도가 급격히 빨라짐
- n8n, Claude Code 같은 노코드/로우코드 툴과 AI의 결합으로 업무 자동화가 일반화
- 데이터 웨어하우스부터 멀티 에이전트 서빙까지 전반적인 워크플로우 이해 필요

### 도메인 지식의 중요성 증대

- 기술적 접근성이 높아지면서 도메인 지식이 더욱 중요한 차별화 요소
- 과거 데이터 엔지니어 역량의 95%가 기술적 측면이었다면, 현재는 도메인 지식의 비중이 크게 증가

### 에이전트 중심 업무 전환

- 사람의 업무를 에이전트에게 위임하고, 사람은 슈퍼바이저가 되는 구조로 진화
- AX 전환(Agent Transformation)이 기업 전반에 확산 중
- 데이터 엔지니어뿐 아니라 마케터, 사업 직군, 인사 직군까지 에이전트 활용이 KPI

### 강의 커리큘럼 및 실전 프로젝트

- 레이크하우스 구축 → 하이브리드 서치/그래프 RAG 구현 → LangGraph 멀티 에이전트 개발 순서로 진행
- Apache Airflow, Kafka, Python 등 오픈소스 기반 기술 스택 활용
- 공공 데이터 또는 가상 데이터를 활용한 실전 프로젝트 포함
- 기술 스택은 회사마다 다를 수 있지만, 전체 워크플로우와 설계 개념을 이해하는 것이 핵심

### Q&A 주요 내용

- **보안 이슈**: 엔터프라이즈급 API 서비스(Gemini, Azure OpenAI 등)는 분리된 환경에서 재학습하지 않아 보안 문제 없음
- **비용 절감**: 1인 개발자는 Hugging Face의 오픈소스 LLM 활용 가능
- **신입 도메인 지식 습득**: 눈높이를 낮춰 원하는 인더스트리의 스타트업이나 소규모 기업에서 경험 쌓기, 현재 회사에서 데이터 핸들링 업무 확장 시도
- **복잡한 테이블 구조**: 프롬프트에 특정 테이블 명시, 시맨틱 처리, 용어사전/메타데이터 활용
- **Feature Store 필요성**: 모델이 한두 개이고 실시간 피처가 불필요한 소규모 프로젝트에서는 선택사
